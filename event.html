The Ingestible Document
Schema-Light JSON
{
  "tx_id": "PAY-9982",
  "sender_id": "USR-01",
  "receiver_id": "USR-02",
  "amount": 250.00,
  "currency": "USD",
  "status": "INITIATED",
  "timestamp": "2026-03-02T10:00:00Z"
}

Each service ingests this simple doc, performs one task, and emits the next event.

Service 1

Balance Guard

Ingests doc → Checks User-01 balance in MongoDB → Emits "BalanceVerified".

Service 2

Fraud Scanner

Ingests doc → Runs ML check on history → Emits "FraudCleared".

Service 3

Ledger Update

Ingests doc → Updates double-entry records → Emits "LedgerSuccess".

Service 4

Notification

Ingests doc → Triggers Push/SMS to user → Payment Cycle Ends.

Why Non-ACID?

  • ✔ Massive Scale: No global database locks. Services process events in parallel across different clusters.
  • ✔ Loose Coupling: Notification service doesn't care if the Fraud scanner is slow or offline. Events queue in Kafka.

Handling Failures

Instead of a Rollback, we use Compensating Transactions. If Service 3 (Ledger) fails, it emits a "PaymentRejection" event, which Service 1 ingests to return the funds.
