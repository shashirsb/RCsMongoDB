DB Logic & Side Effects

Stored Proc: SP_VALIDATE_AND_DEBIT

Orchestrates the 12-table logic. Complexity increases exponentially with every added business rule.

Trigger: TRG_AUTO_AUDIT

Fires on every update to ACCOUNTS. Forces a synchronous write to AUDIT_LOG table before original update finishes.

Sequence: SEQ_GLOBAL_TX_ID

Shared resource. High contention point for parallel payments.

The Heavy Rollback

If a failure occurs at table #10 (Tax Records), Oracle must:

  • 1. Reverse the Trigger's Audit Row.
  • 2. Restore the LEDGER balance from UNDO logs.
  • 3. Revert the sequence pointer cache.
  • 4. Traverse 12 physical data files to release row locks.

Performance Impact: High Latency / Low Throughput

Oracle PL/SQL (Complex Join & Side Effects) 

CREATE OR REPLACE PROCEDURE sp_complex_bank_transfer(
    p_sender_id IN VARCHAR2, 
    p_receiver_id IN VARCHAR2, 
    p_amount IN NUMBER
) AS
    v_daily_spent NUMBER;
    v_max_limit   NUMBER;
BEGIN
    -- 1. Explicit Row Locking (Pessimistic) across Join
    SELECT l.spent_today, l.daily_limit 
    INTO v_daily_spent, v_max_limit
    FROM accounts a
    JOIN account_limits l ON a.acc_id = l.acc_id
    WHERE a.acc_id = p_sender_id
    FOR UPDATE OF a.balance, l.spent_today;

    -- 2. Business Logic Validation within the DB Layer
    IF (v_daily_spent + p_amount > v_max_limit) THEN
        RAISE_APPLICATION_ERROR(-20001, 'Daily Limit Exceeded');
    END IF;

    -- 3. Complex Multi-Table State Update
    UPDATE (
        SELECT a.balance, l.spent_today, u.last_activity
        FROM accounts a
        JOIN account_limits l ON a.acc_id = l.acc_id
        JOIN users u ON a.user_id = u.user_id
        WHERE a.acc_id = p_sender_id
    ) SET balance = balance - p_amount, 
          spent_today = spent_today + p_amount,
          last_activity = SYSDATE;

    -- 4. Audit Trail with Sequence & Trigger dependencies
    INSERT INTO audit_log (log_id, acc_id, action, amount, branch_code)
    VALUES (seq_global_tx.NEXTVAL, p_sender_id, 'TRANSFER_OUT', p_amount, 
           (SELECT branch_id FROM branches WHERE is_active = 'Y' AND rownum = 1));

    -- 5. Global Ledger Reconciliation
    UPDATE ledger SET total_reserve = total_reserve - p_amount 
    WHERE currency_type = 'USD' AND status = 'OPEN';

    COMMIT; -- All locks released only at this point
EXCEPTION 
    WHEN OTHERS THEN
        ROLLBACK; -- Every row in Audit, Ledger, and Accounts must be physically reverted
        RAISE;
END;

Result: 4 Table locks, 1 Sequence increment, and 1 Undo segment entry.

MongoDB withTransaction (Atomic Document Update) 

const session = client.startSession();
session.startTransaction();

try {
  // 1. Operational Update: Unified User & Account State
  await userAccounts.updateOne(
    { _id: 'U1' }, 
    { $inc: { balance: -200, "limits.daily_rem": -200 } }, 
    { session }
  );

  // 2. Telemetry: Immediate Audit Log
  await auditLogs.insertOne(
    { tx_id: 'TX_99', acc_id: 'U1', action: 'DEBIT', ts: new Date() }, 
    { session }
  );

  // 3. System State: Branch Ledger Sync
  await ledger.updateOne(
    { branch_id: 'B01' },
    { $inc: { total_assets: -200 } },
    { session }
  );

  // 4. Persistence: Atomic Multi-Doc Commit
  await session.commitTransaction();
} catch (error) {
  // 5. Resilience: Full Rollback on Failure
  await session.abortTransaction();
} finally {
  session.endSession();
}

Result: Single Document Lock. Optimized for high-throughput concurrency.

Do you still need to do a transaction?

Cross-Document (YES)

Required when moving data between independent entities (e.g., User A to User B). Ensures consistency across the replica set.

Intra-Document (NO)

Updates within a single user context are already atomic. Transactions here add unnecessary overhead to your application.
