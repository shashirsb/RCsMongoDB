Below is a deep, topology‑by‑topology breakdown of how **MongoDB replica set failover** works, with as much detail as is useful for design and explaining to others.

I’ll assume current MongoDB behavior with **replication protocolVersion: 1**, default **electionTimeoutMillis = 10,000 ms** (10s).

---

## 1. Core failover & election mechanics (applies to all topologies)

### 1.1 Health detection

- Every member sends **heartbeats every 2 seconds** to every other member.  
- If a member doesn’t get a heartbeat response from another node within **10 seconds** (default `electionTimeoutMillis`), it marks that node as **inaccessible** and may initiate an election.

Timeline (defaults):

- **t = 0s** – primary crashes or becomes unreachable.
- **t ≈ 2, 4, 6, 8s** – secondaries keep sending heartbeats.
- **t ≈ 10s** – secondaries conclude “primary is down/unreachable”.
- Immediately after, an eligible secondary **calls for election**.
- Total time to detect + elect is typically **≤ ~12 seconds** (10s detection + a couple seconds for election and term change).

`electionTimeoutMillis` can be tuned:

- **Higher** → slower failover, less sensitivity to transient latency.
- **Lower** → faster failover, more sensitivity → potentially **more elections & rollbacks for w:1 writes**.

### 1.2 When is an election triggered?

Elections can start when:

- A new node is added/initiated.
- `rs.stepDown()` / `rs.reconfig()` reconfigures or steps down primary.
- Secondaries lose connectivity to the primary beyond `electionTimeoutMillis` (10s default).
- Network partition or DC loss creates a **partition with a majority** and one with a minority (see below).

### 1.3 Election algorithm (high‑level)

Key rules:

- Only **voting members** (`members[n].votes = 1`) can vote or be counted in majority.
- Only members with **`priority > 0`** can run for primary. `priority = 0` members never become primary.
- A candidate asks other voting members to vote for it; it must:
  - See itself as having **up‑to‑date data** (relative to others) and
  - Collect a **majority of votes** (e.g., ≥2 out of 3, ≥3 out of 5).
- **Member priority** biases *who* becomes primary:
  - Higher‑priority secondaries will **call elections sooner** and are **more likely to win**.
  - Replica set keeps holding elections until the **highest‑priority available** node becomes primary (priority takeover).

### 1.4 Network partitions & majority rule

- If a **primary sees only a minority** of voting members, it **steps down** to secondary.
- In the partition that has a **majority of voting nodes**, one member calls an election and becomes the new primary.
- This majority rule prevents two primaries from both being able to acknowledge `{ w: "majority" }` writes at the same time.

### 1.5 Client / driver behavior during failover

- During election:
  - No node is primary → **no writes accepted** until election completes.
  - Reads may proceed from secondaries if read preference allows.
- Modern drivers:
  - Detect loss of primary and **discover new primary** automatically.
  - Retry certain write operations **once** (retryable writes) to mask short failovers.

## 2. One region – 1 replica set – 3 nodes

Typical layout (good practice):

- **Region A**:
  - Node 1: primary (priority 2)
  - Node 2: secondary (priority 1)
  - Node 3: secondary (priority 1)  
- All 3 are voting members.

### 2.1 Primary failure in the same region

1. **Normal state**
   - All nodes exchange heartbeats every 2s.
   - Primary handles all writes; secondaries tail its oplog.

2. **Primary crashes at t = 0**
   - Node 2 & 3 stop receiving heartbeats from Node 1.

3. **Detection**
   - After ~10s of missing heartbeats, Node 2 and/or 3 mark Node 1 as down.

4. **Election call**
   - One secondary calls an election (typically the one with **higher priority**, or with the most up‑to‑date state).

5. **Voting**
   - Both secondaries (plus the failed node’s “no vote”) → 2 votes available.
   - Candidate needs **2/3 majority** → both live nodes vote for one → that node becomes primary.

6. **Post‑election**
   - Cluster resumes writes on new primary.
   - Total write unavailability ≈ 10–12 seconds.

### 2.2 Secondary failure

- If a **secondary fails**:
  - Primary + one secondary remain → still **2 voting nodes = majority**, no election needed unless primary fails later.
  - Writes continue normally.
  - If primary later fails with only one secondary left (2/3 down), no majority → **no primary can be elected** → writes halted until another node returns.

### 2.3 Region‑level issues

Because all nodes are in one region:

- Loss of the **entire region** = loss of the replica set.
- Failover protects primarily against:
  - Individual node crashes.
  - Software restarts / rolling upgrades.
  - Intra‑region network blips.

## 3. Two regions – 1 replica set – 3 nodes

There are two common patterns:

- **(A) 2+1 pattern (recommended)**:  
  - Region A: 2 voting nodes (one preferred primary, one secondary).  
  - Region B: 1 voting secondary.
- **(B) 1+2 pattern**:  
  - Region A: 1 voting node.  
  - Region B: 2 voting nodes.

I’ll assume you’ll put the **preferred primary** where most writes originate (e.g., Region A) via **priority**.

### 3.1 2+1 pattern (Region A = “home”)

Example:

- Region A:
  - Node 1: primary, priority 2
  - Node 2: secondary, priority 1
- Region B:
  - Node 3: secondary, priority 1  
- All 3 are voting.

#### 3.1.1 Failure of primary only (Region A still up)

Same as single‑region 3‑node case:

- Node 2 / Node 3 detect Node 1 down after ≈10s.
- One of them calls election; because Node 2 is **closer** and similarly prioritized, usually Node 2 takes over.
- Region A continues to host primary; Region B remains secondary.

#### 3.1.2 Loss of Region A entirely (both Node 1 & 2)

- Remaining nodes:
  - Region B: only Node 3 (1 vote).
- Majority required = 2 (out of 3 voting members).
- Node 3 does **not** have majority → it **cannot become primary**.  
  - It stays secondary; no primary anywhere.
- Result:
  - Reads from Node 3 (read preference allowing secondaries) still possible.
  - Writes **blocked** until Region A returns or you manually reconfig to change membership.
- Implication:
  - **2+1 is *not* region‑failover resilient** – it is resilient to *one node* loss in Region A, but not **region loss** of A.

#### 3.1.3 Loss of Region B (Node 3)

- Remaining:
  - Region A: Node 1 (P), Node 2 (S) → 2 votes (majority).
- If Node 1 later fails:
  - Node 2 still has majority (2/3 configured votes are reachable) and can become primary.
- So loss of Region B is **fine** from availability perspective.

### 3.2 1+2 pattern (Region B has majority)

Example:

- Region A:
  - Node 1: primary, priority 2
- Region B:
  - Node 2: secondary, priority 1
  - Node 3: secondary, priority 1

You would normally **not** make Region A the primary in this layout, because:

- If Region A (with 1 node) fails, Region B (2 nodes) has majority and can elect a new primary – good.
- If Region B (2 nodes) fails, Region A (only Node 1) loses majority → Node 1 steps down / cannot be primary.

So recommended practice if you want **survive Region A loss**:

- Put primary in **Region B** (the 2‑node region), not in Region A.
- That way:
  - Losing Region A (single node) → Region B still 2/3 → elect primary.
  - Losing Region B (two nodes) → no majority → no primary (expected).

## 4. Three regions – 1 replica set – 3 nodes (1–1–1, “highly resilient”)

Topology:

- Region A:
  - Node 1: primary, priority 2
- Region B:
  - Node 2: secondary, priority 1
- Region C:
  - Node 3: secondary, priority 1

All 3 are voting. This is a **geographically distributed** RS; MongoDB docs explicitly discuss DC loss for such setups.

### 4.1 Loss of any single region

If any **single region** is lost:

- Remaining nodes = 2 (one in each of the two surviving regions).
- Majority of 3 = 2 → the two remaining nodes **have majority**.

Scenarios:

1. **Region A (primary) lost**
   - Region B & C:
     - Detect loss of primary after ≈10s.
     - One of them calls election; both accessible → election success.
     - New primary chosen (priority can bias which region wins).
   - Cluster remains available for writes after ~12s.

2. **Region B lost while primary is in Region A**
   - Remaining: A (P), C (S) → 2/3 majority → no election needed.
   - If later A fails too, single remaining node C cannot be primary.

3. **Region C lost** – symmetric to Region B loss.

This topology is **region‑resilient for any single region** failure, as long as **network connectivity between the other two regions is healthy**.

### 4.2 Network partitions

With 3 regions, key partition patterns:

1. **Region A isolated; B and C can see each other**

   - A (with primary) can see only 1/3 voting nodes (itself) → minority.
   - By rule, primary in minority **steps down** and becomes secondary.
   - B or C (seeing 2/3) call election → one becomes new primary.
   - Clients connected to A should be routed away (F5/DNS-level steering).

2. **Triangle split – each region can see only itself** (rare, but worst case)

   - All regions have view = 1/3 nodes (self only).
   - No region has majority → **no primary anywhere**.
   - All nodes operate as secondaries; writes blocked.

3. **A + B connected, C isolated** – majority (A,B) ≈ fine.

Architecture best practice:

- Ensure **the network is designed** such that **at most one region** ever becomes isolated at a time (with the others still interconnected), so that at least one partition always holds a majority.

### 4.3 Priority planning

- You typically:
  - Give **Region A** the highest priority (e.g., 2).
  - Regions B and C at priority 1.
- Behavior:
  - After any failover, RS **eventually converges** to primary in Region A, if it’s up and reachable; until then, B or C can serve as primary.

## 5. Three regions – 1 replica set – 5 nodes (3R‑5N, “highly resilient”)

To tolerate **any single region failure** while minimizing risk, a common high‑resilience layout is:

- Region A (home / primary region): **2 electable voting nodes**
- Region B (secondary region): **2 electable voting nodes**
- Region C (DR / tie‑breaker region): **1 electable voting node**

All 5 are voting (`votes = 1`), majority required = **3**.

Example:

- Region A:
  - Node 1: primary, priority 2
  - Node 2: secondary, priority 1
- Region B:
  - Node 3: secondary, priority 1
  - Node 4: secondary, priority 1
- Region C:
  - Node 5: secondary, priority 0.5 (still > 0 so eligible primary)

(You might also set Region C’s node to low but non‑zero priority so it can be primary only if both A and B are badly impacted.)

### 5.1 Region failure analysis

We check **loss of each region**:

1. **Lose Region A (2 nodes)**
   - Remaining:
     - Region B: 2 nodes
     - Region C: 1 node → total 3 voting nodes.
   - Majority of 5 = 3 → surviving nodes have majority.
   - They elect a new primary (probably in Region B by priority).
   - RPO: none (normal replication); RTO: ≈ 10–12 seconds.

2. **Lose Region B (2 nodes)**
   - Remaining:
     - Region A: 2 nodes
     - Region C: 1 node → total 3 nodes.
   - Majority still satisfied; A or C becomes primary (most likely in A).

3. **Lose Region C (1 node)**
   - Remaining:
     - Region A: 2 nodes
     - Region B: 2 nodes → 4 nodes total.
   - Majority (3) is still available; failover behaves like a 4‑node (really 4‑voting) ensemble.

So with **2‑2‑1** distribution of voting nodes, **any single region loss still leaves ≥3 votes**, which is a majority of the 5 configured votes.

### 5.2 Network partitions

Key patterns with 2‑2‑1:

1. **Region A isolated; B + C connected**

   - A sees only its 2 votes (Nodes 1,2) → **2 < 3** ⇒ no majority → primary in A steps down.
   - B + C have 3 votes (Nodes 3,4,5) → majority → elect primary in B/C.
   - Good: quorum remains on the **pair + singleton** side.

2. **Region B isolated; A + C connected**

   - Symmetric to above; A + C will hold primary.

3. **C isolated; A + B connected**

   - AB side has 4 votes (≥3) → keeps/ elects primary there.
   - C side (single node) never gets majority and acts as secondary.

4. **Pathological 3‑way split (each region only sees itself)**

   - A has 2, B has 2, C has 1; no side has 3 → no primary anywhere.
   - This is a network design problem; topology can’t fix a 3‑way majority loss.

### 5.3 Electability & priorities

You can further refine for “operational” resilience:

- **Electable sets**:
  - For example, make **A and B electable (priority ≥1)** and make **C low priority but >0** so C becomes primary only as last resort.
- Hidden/Non-voting options:
  - You may turn some nodes into **priority 0** (hidden/analytics) or **non‑voting** if you need more than 7 total members or if you want them never to be primary.
  - But for the specific **5‑node failover majority design**, typically all 5 remain voting.

## 6. Extra fine‑grained details that matter in practice

### 6.1 Election timing knobs

- **`settings.electionTimeoutMillis`** (per RS config):
  - Default `10000` (10s).
  - Lower for faster failover; higher for noisy/latency‑sensitive networks.

- **`settings.catchUpTimeoutMillis`**:
  - Window for **newly elected primary to catch up** with others before accepting writes.
  - Longer catch‑up → fewer rollbacks but slower failover.

### 6.2 Mirrored reads & cache warm‑up

- MongoDB can mirror a portion of primary reads to electable secondaries to **pre‑warm their cache**, so when a secondary becomes primary after failover, it already has hot working set and performance dip is smaller.

### 6.3 Majority, votes, and topology limits

- Up to **50 members**, but only **7 voting** members maximum.
- Voting members must satisfy:
  - `votes ∈ {0,1}`; arbiters always `votes = 1`.
  - `priority > 0` ⇒ `votes` cannot be 0.
  - `votes = 0` ⇒ `priority` must be 0 (non‑voting and never primary).

These constraints are the reason patterns like **3 nodes (1–1–1)** or **5 nodes (2–2–1)** are the “sweet spot” for multi‑region resilience.
